# Feature History

- **Database Setup (Prisma 7 + Neon):** Added Prisma 7 with the `@prisma/adapter-neon` driver adapter. `prisma/schema.prisma` uses the `prisma-client` generator (output `generated/prisma`, git-ignored, built by `postinstall`) with a URL-less datasource; `prisma.config.ts` takes the direct `DATABASE_URL_UNPOOLED` for the CLI and migrations. `lib/db.ts` exports one `server-only` client on the pooled `DATABASE_URL`, cached on `globalThis` outside production. First migration `init_user` contains only the `User` model and its `[isDemo, demoExpiresAt]` index, applied to the Neon `development` branch (the `production` branch is untouched); later features add their own models. Vitest is configured with the `@/` alias and node environment, with a shared `test/mock-prisma.ts` and a smoke test in `lib/users.test.ts`, so tests never reach Neon. `prisma` is pinned to 7.x because npm's default is an 8.0 release candidate. `.env.example` is committed with empty values. Specs now call the Neon dev branch `development`. Vercel still needs `npx prisma migrate deploy && next build` as the build command, with both DB env vars scoped per environment.

- **Authentication (Clerk Sign-in & Registration):** Added Clerk (`@clerk/nextjs` 7) with email/password and Google sign-in. `/sign-in` and `/register` live in the `app/(auth)` route group using Clerk's `SignIn`/`SignUp`. `proxy.ts` (Next.js 16's rename of middleware) protects everything except `/`, the auth pages and `/api/webhooks/clerk`; signed-out requests redirect to `/sign-in`. The root layout puts `ClerkProvider` inside `<body>` and wraps auth-reading parts in `<Suspense>`, which `cacheComponents: true` requires. The navbar shows Clerk's `UserButton` via `<Show when="signed-in">` (Clerk 7 removed `SignedIn`), and `/` redirects signed-in users to `/projects` (a placeholder page until the Projects feature). `/api/webhooks/clerk` verifies with `verifyWebhook` and upserts on `user.created` or deletes on `user.deleted`, returning 500 on DB errors so Clerk retries. `lib/users.ts` holds Zod-validated upsert/delete helpers; `lib/auth.ts` `getCurrentUser()` creates the `User` on first request if the webhook has not arrived. No new migration. Vitest covers the webhook, fallback and helpers. Not verified: a real sign-up, Google sign-in, or a signed webhook delivery; `CLERK_WEBHOOK_SIGNING_SECRET` was not yet set. Known gaps: a missing signing secret returns 400 instead of 500, `user.updated` is not synced, a unique-email conflict would make the webhook retry, and unauthenticated API calls get a redirect instead of a 401.

- **Projects:** Added multiple books per user. - **Project Accent Color:** Inside a project, the accent follows the cover color. `lib/accent.ts` `getAccentTokens` turns a `#rrggbb` cover color into `primary`, `primary-foreground` and `ring` for the dark theme: it keeps the hue, lightens in HSL until the color has at least 4.5:1 contrast on `#0a0a0a`, and picks `#0a0a0a` or white text by contrast; invalid input returns null so the default palette stays. 43 unit tests cover all 8 presets and extremes (pure black and white, near-black navy, saturated primaries, grey). - **Read Caching:** the database reads behind the project pages are cached, so switching between characters, scenes, sections and projects no longer queries the database for anything that has not changed. Server cache: `getProject`, `getManuscript`, `getScene`, `getWordStats`, `listProjects` (lib/projects.ts, lib/manuscript.ts) and `listCharacters`, `getCharacter`, `listCharacterNotes` (lib/characters.ts) use `"use cache"` with `cacheLife("days")` and a `cacheTag` for what each depends on, defined in `lib/cache-tags.ts`; the user id is a function argument, so it is part of every cache key and one user can never read another's entry. The word totals take the UTC day as an argument so they roll over at midnight. Invalidation: every Server Action that writes calls `updateTag` with the matching tags (actions/characters.ts, actions/manuscript.ts, actions/projects.ts), so the next read is fresh and a stale entry is never served after a write. Autosaving a scene expires only that scene, the word totals and the project list (its "Edited" date and order change), not the outline, which never shows a scene's word count. Renaming a node expires the outline and that scene; editing or deleting a project expires its `project` tag, which every read of that project carries, and so everything cached for it. Browser cache: `experimental.staleTimes.dynamic = 300` in `next.config.ts` keeps visited pages for 5 minutes so going back to one needs no server request; Next clears that cache whenever a Server Action calls `updateTag` or `revalidatePath`, which all of ours do. Character, scene and project links also call `router.prefetch` on pointer enter and focus, so a first visit is usually served from the browser. A test harness change: `test/mock-prisma.ts` now also mocks `next/cache`, so the `use cache` helpers do nothing in unit tests; new tests pin which tags each action expires. 206 unit tests pass, typecheck, lint and `npm run build` pass. Measured on a production build with a temporary probe route (removed): cached reads took 0 to 2 ms against 34 to 415 ms cold; a plain Neon round trip was about 35 ms. Developer-tried: switching characters, scenes and projects on a production build ("production caching working"); not retried by the developer after the project-list change. Known gaps: the default cache handler is in memory, so it only persists on a self-hosted server and on serverless hosting entries may not survive between requests (`use cache: remote` or a custom `cacheHandlers` is the fix); a change made on another device can show up to 5 minutes late in a tab that already holds the page; the first visit to something not hovered or opened still waits on the server; `getCurrentUser` still reads the user row on every request (about 40 ms); no component tests. - **Demo User:** a **Try demo** button on the landing page (in the logo's indigo) signs a visitor into a temporary, seeded account with no sign-up. Flow: `POST /api/demo` (`app/api/demo/route.ts`) calls `startDemo` (`lib/demo.ts`), which returns a one-use Clerk sign-in ticket (`clerkClient.signInTokens`, 60 s) that the browser redeems with `signIn.ticket()` and `finalize` (`components/demo/TryDemoButton.tsx`), then lands on `/projects`. One live demo per IP: the caller's IP (`x-forwarded-for`, a fixed address in development, refused in production when missing) is hashed with an HMAC keyed by `DEMO_COOKIE_SECRET` (`lib/demo-ip.ts`) and claimed in Upstash Redis with `SET NX EX 43200` (`lib/demo-store.ts`). Because the Upstash database is shared with other projects, every key lives under `prosestack:demo:` (`ip:<hash>` and a reverse `user:<clerkId>`), and the code only ever runs SET NX EX, GET, DEL and a keep-TTL SET XX on those keys, never a scan or flush. The slot holds a `pending:<uuid>` marker while the demo is created, then the Clerk id; a concurrent press from the same IP waits (polling, up to 6 s) and signs into the winner's demo, so exactly one demo survives, and a stale slot that names a missing or expired demo is freed. A signed, httpOnly resume cookie (`lib/demo-cookie.ts`, HMAC with a timing-safe compare, carries the Clerk id and expiry) signs a visitor back in when their IP changed. If Redis errors the demo is refused with 503 and no Clerk user is created (fail closed), while the cookie path still works. Creation: a Clerk user with generated `demo-<uuid>@example.com`, no password and `publicMetadata { isDemo, demoExpiresAt }`, then one transaction that upserts the `User` row (`isDemo`, `demoExpiresAt = now + 12 h`; upsert because the Clerk webhook may have created it first) and seeds the project (`lib/demo-seed.ts`: "The Lighthouse Keeper" with two parts, three chapters, five scenes with text and word counts, four characters with sketches and notes, all by bulk `createMany`). Any failure rolls back each step independently (Clerk user, database row, IP slot). Expiry: `getCurrentUser` redirects an expired demo to `/demo-expired`, a public page that signs the visitor out, so a demo is blocked at request time even before cleanup runs; a banner (`components/demo/DemoBanner.tsx`) shows hours left and a Register button that signs out first (demos cannot be converted). Cleanup: `GET /api/cron/cleanup-demos` (`CRON_SECRET` bearer, timing-safe compare) runs `cleanupDemos` (`lib/demo-cleanup.ts`): expired demos are deleted Clerk-first, then the database user (everything cascades), then the IP slot; a failed Clerk delete leaves the row for the next run; a 404 counts as already gone; an orphan sweep lists Clerk users by the `demo-` query, requires `isDemo` metadata and the demo email domain, and removes ones with no database row (after a 10 minute grace for in-flight creations) or whose metadata says they expired. `vercel.json` schedules it daily (Hobby limit). The public routes `/api/demo`, `/api/cron/cleanup-demos` and `/demo-expired` were added to `proxy.ts`. New env vars `DEMO_COOKIE_SECRET` and `CRON_SECRET` (in `.env.example`; local `.env` and `.env.production` got generated values; they must also be set in the Vercel project). Process change: the feature review step now checks that features adding user-created data (places, research, plot lines and points) also extend the demo seed, recorded in `demo-spec.md` and in memory. 271 unit tests pass (new: cookie, IP, seed, store with an in-memory Redis, orchestration including races, fail-closed and rollback, cleanup, the cron route's auth, expired-demo redirect), typecheck, lint and `npm run build` pass. Verified against the real services with throwaway data that was deleted afterwards: Upstash claim/NX/KEEPTTL behaviour and Clerk create-user, sign-in token and list query. Developer-tried in the browser: Try demo ("looking great"). Not tried: resuming from a second browser on the same IP, the expiry redirect, the cron route in production, behaviour on Vercel. Known gaps: plot lines, places and research are not seeded yet (their features don't exist; each adds its own seed rows); a shared IP (office, school, carrier) shares one demo, as the spec accepts; the shared Upstash free-tier quota can be used up by the other projects, which would block new demos (fail closed); the Clerk instance must not require a username; Vercel Hobby runs the cleanup only once a day, so expired demos linger up to 24 h in Clerk (blocked from use meanwhile); uploads don't exist yet, so nothing is disabled for demos.
