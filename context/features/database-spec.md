# Database Setup (Prisma 7 + Neon) — Feature Spec

Source: [project-overview.md](../project-overview.md) §4 Tech Stack (Prisma 7 setup notes, Environment variables), §5 Architecture, §6 Data Model, §7 Prisma Schema, §11 Development Rules.

## Summary

The foundation for all persistence: Prisma 7 connected to Neon through the driver adapter, a single shared client, the first migration (`User` only), and a Vitest setup that mocks the database. Every other feature builds on this one.

## Requirements

### Dependencies
- Runtime: `@prisma/client`, `@prisma/adapter-neon`, `zod`.
- Dev: `prisma`, `dotenv`, `vitest`.
- Scripts in `package.json`: `test` (`vitest run`), `test:watch` (`vitest`), `postinstall` (`prisma generate`).

### Prisma config
- `prisma/schema.prisma`: generator `prisma-client` with `output = "../generated/prisma"`; datasource `postgresql` with **no URL** (Prisma 7).
- `prisma.config.ts` at the repo root: `schema`, `migrations.path`, and `datasource.url` from `DATABASE_URL_UNPOOLED` (direct connection, used by the CLI and migrations).
- Add `generated/` to `.gitignore`; the client is generated by the `postinstall` script (`prisma generate`), so it exists after any `npm install`, locally or on Vercel. `prisma generate` only reads `schema.prisma` and needs no database connection.

### Client
- `lib/db.ts` exports a single `prisma` instance using `PrismaNeon` with the **pooled** `DATABASE_URL`, cached on `globalThis` outside production.
- Import the client from `@/generated/prisma/client`, never from `@prisma/client`.
- Server-only: the module imports `server-only` so it cannot be bundled into client components.

### Initial schema and migration
- First migration, `init_user`, contains only the `User` model and its index from overview §7 (`clerkId` unique, `email` unique, `isDemo`, `demoExpiresAt`, `@@index([isDemo, demoExpiresAt])`).
- **Each later feature adds its own models in its own migration** (Projects adds `Project`, Manuscript adds `ManuscriptNode`, and so on). The full schema in overview §7 is the target, not a single migration.
- Migrations are created with `npx prisma migrate dev --name <name>` and applied in production with `npx prisma migrate deploy`.
- **Never use `prisma db push`** or change the database structure by hand.

### Environment
- `.env.local` (git-ignored) holds `DATABASE_URL` (pooled) and `DATABASE_URL_UNPOOLED` (direct).
- Commit a `.env.example` listing every variable with empty values; update it as features add variables.
- Two Neon branches: **`dev`** (local work and Vercel Preview) and **`production`** (Vercel Production). Test migrations on `dev` before they reach `production`.

### Deployment (Vercel)
- Build command: `npx prisma migrate deploy && next build`. `migrate deploy` only applies migrations; the client comes from `postinstall`.
- Set both `DATABASE_URL` and `DATABASE_URL_UNPOOLED` in Vercel, scoped by environment: Production points at the `production` branch, Preview points at the `dev` branch. The build command runs on every build, so an unscoped variable would let a preview build migrate production.

### Data access conventions
- Every query is scoped by the signed-in user's `userId` (and `projectId` where applicable); never trust client-supplied ownership.
- Validate all server input with Zod before it reaches Prisma.
- Prefer a small helper per entity under `lib/` (or alongside actions) over calling `prisma` directly from components.
- Multi-row changes that must stay consistent (reordering, trashing a subtree) run in `prisma.$transaction`.

### Testing
- Vitest configured in `vitest.config.ts` with the `@/` path alias (maps to the repo root, as in `tsconfig.json`), a `node` environment, and `include: ["**/*.test.ts"]` excluding `node_modules` and `.next`.
- Tests mock `@/lib/db` (for example with `vi.mock`) and **never touch Neon**.
- Provide a shared helper (for example `test/mock-prisma.ts`) so feature tests do not each rebuild the mock.
- One smoke test proves the setup: a trivial server-side function using the mocked client.
- Unit tests only for server actions and utilities; no component tests.

## Data
- `User` only, at this stage (see above).

## Env vars
`DATABASE_URL`, `DATABASE_URL_UNPOOLED`.

## Acceptance criteria
- `npx prisma migrate dev` applies `init_user` to the Neon dev branch without errors.
- `npx prisma generate` produces the client at `generated/prisma`, and TypeScript resolves `@/generated/prisma/client`.
- A server-side call such as `prisma.user.count()` succeeds against the dev branch.
- `npm test` runs and passes without any database connection or env vars.
- `npm run build` passes, and `lib/db.ts` cannot be imported from a client component.
- `.env.local` and `generated/` are git-ignored, and `.env.example` is committed.
